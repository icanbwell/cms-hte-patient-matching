# How this tool was built, and how to reproduce or extend it

This document covers the *process* behind `calculations/` — why it's shaped the way it is, how
the source URLs were resolved, and how to re-run or extend it. For the actual results (the
u-probability numbers, per-field methodology, and caveats), see
[`outputs/u_probabilities.md`](../outputs/u_probabilities.md) — that file is generated by
`run_all.py`, not hand-written, so it's always in sync with the latest run.

## Why this exists

The patient-matching model uses hand-picked, deliberately conservative u-probabilities (the
probability two distinct people agree on a field) for each match field. This tool checks those
conservative values against empirical estimates computed from public Census/ACS data, so the
conservative values can be justified — or revisited — with real numbers instead of intuition.

## Why it's a separate, standalone project

`calculations/` does not import from `patient_matching/` and isn't wired into this repo's
pyproject.toml, uv.lock, or CI. It's a one-off analysis tool with its own dependency set
(`rapidfuzz`, `openpyxl`, etc.) that has no reason to ship with the matching library itself, and
keeping it isolated means it can't accidentally affect the matching package's dependency
resolution or test suite. If findings from this tool motivate a change to the model's u-values,
that change belongs in `patient_matching/` as its own, separately-reviewed change — this tool
only produces the evidence, not the conclusion.

## Project shape

```
calculations/
  config.py     # resolved source URLs (with provenance comments), conservative-u constants, sanity ranges
  download.py   # idempotent downloaders for every source config.py names
  compute.py    # one pure, unit-tested function per field -- no I/O
  run_all.py    # orchestrates download -> compute -> write outputs/, with fuzzy-match checkpointing
  tests/        # synthetic-fixture unit tests for compute.py
  data/raw/         # downloaded source files (gitignored)
  data/processed/   # fuzzy-match ball-mass checkpoints (gitignored)
  outputs/          # u_probabilities.csv / .md (generated, checked in)
```

The download/compute/orchestrate split matters for reproducibility: `compute.py` takes only
already-downloaded files as input and has no network or filesystem side effects beyond reading
them, so every number in `outputs/` can be regenerated from `data/raw/` without re-downloading,
and the unit tests in `tests/` can exercise the math against small synthetic fixtures without
touching real data at all.

## How the source URLs were resolved

Per the original spec, no URL is hardcoded without having been verified to actually resolve.
Each one in `config.py` was found by starting from the public Census/HUD landing page named in
the spec and following it to the current file link (via a real fetch, not a guess), and each has
a comment recording which landing page it came from and the date it was verified. A few
resolution notes worth keeping in mind if these need to be re-resolved later (Census reorganizes
these paths periodically):

- **2020 Census "last names" file** publishes only race/Hispanic-origin cross-tabs, not a single
  plain national last-name list the way the 2010 file does. `compute.py` sums the race columns
  (verified to equal the total `FREQUENCY` column) rather than treating this as a missing file.
- **`www2.census.gov`** intermittently served a cached WAF/Cloudflare rejection page for some of
  these files during development; `download.py` appends a cache-busting query parameter to work
  around it. If downloads start failing with a non-CSV/XLSX response body, check for this first
  before assuming the URL moved.
- **ACS vintage**: the code requests 2024 5-year ACS estimates because 2025 5-year estimates
  were not yet published as of the last run (2026-09-30). `config.py`'s ACS year is a single
  constant — bump it once the next vintage is out, and re-run.
- **First names** *are* present in the 2020 Census release, so the SSA baby-names fallback the
  spec asked for (in case they weren't) exists in `download.py` but is currently unused dead
  code from the tool's perspective — it's there specifically so it activates automatically if a
  future Census release drops first names again, not because it's expected to run today.

## Design decisions worth knowing before extending this

- **Fuzzy name matching** uses a SymSpell-style deletion-neighborhood index to find all other
  listed names within one Damerau-OSA edit (insert/delete/substitute/adjacent transposition),
  then verifies every candidate exactly with `rapidfuzz` rather than trusting the approximate
  index alone. This is what makes it tractable over ~156k surnames — a naive all-pairs
  comparison would be the square of that. Names under 5 characters are excluded from fuzzy
  matching (too many one-edit collisions to be a meaningful "fuzzy" ball) and fall back to their
  exact-match probability instead.
- **Checkpointing**: the fuzzy-match ball-mass arrays for first and last names are cached to
  `data/processed/*_ball_mass.npy` because that computation is the slowest step in the pipeline.
  `run_all.py` reuses a checkpoint if present instead of recomputing — delete the relevant `.npy`
  file to force a recompute (e.g. after changing the edit-distance logic in `compute.py`).
- **Two u estimators are reported everywhere**: `u_simple` (`Σ(n_v/N)²`, plug-in) and
  `u_unbiased` (`Σ n_v(n_v-1)/(N(N-1))`, the finite-population pairs estimator). `u_unbiased` is
  the headline number throughout, per the original spec, because it's the estimator that
  actually answers "probability two *distinct* people agree," not "probability two independent
  draws agree."
- **Suppression handling for name files**: Census only lists names above an occurrence
  threshold. Rather than pick one answer, every name-based u reports two bounds — (a) listed
  names renormalized to their own total (the headline), and (b) listed names plus the unlisted
  remainder treated as all-singletons (a lower bound) — so the suppression effect is visible
  rather than hidden inside a single number.
- **Street-line-and-ZIP is a deliberately named floor, not a point estimate.** It models only
  the "two people share a household" effect and explicitly ignores street-name collisions
  between unrelated households in the same ZIP, so its huge ratio against the conservative value
  (see `outputs/u_probabilities.md`) should not be read as evidence the conservative value is
  wrong by that much — it's a known-loose lower bound by design.

## How to reproduce

See the Setup/Running sections in [`README.md`](../README.md). In short: `python3.12 -m venv
.venv`, install `requirements.txt`, optionally drop `CENSUS_API_KEY`/`HUD_TOKEN` into a
gitignored `calculations/.env`, then `python run_all.py` and `pytest tests/`. Both `data/raw/`
and `data/processed/` are gitignored and fully reproducible from `run_all.py` alone — nothing in
those directories should be assumed durable or edited by hand.

## Extending this later

Two pieces of the original spec were left as documented gaps rather than blocking completion:

- **HUD USPS ZIP↔city crosswalk**: skipped because no `HUD_TOKEN` was configured. `download.py`
  prints exact manual-registration instructions when this happens. Once a token is available,
  set `HUD_TOKEN` in `.env` and re-run — `compute.py`'s city calculation will pick up the
  alternate USPS-city-via-ZIP allocation automatically.
- **PUMS independence check** (joint u for age × sex × PUMA vs. product of marginals) and
  **top-10-value reporting for tail concentration** were listed as "if time allows" in the
  original spec. Top-10 reporting is implemented (see each field's section in
  `outputs/u_probabilities.md`). The PUMS joint-independence check is not yet implemented; it
  would need the ACS PUMS person file (`AGEP`, `SEX`, `PUMA`, `ST`, `PWGTP` columns only) added
  as a new source in `config.py`/`download.py` and a new function in `compute.py`.
